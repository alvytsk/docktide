# M4 Images Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An Images page built for cleanup: usage and unique size per image, guarded removal (one, selected, all unused), build cache size and clear, and an image details page.

**Architecture:** A new `images` module in `docktide-core` lists, inspects, and removes images (guarded by an exact `ImageID` check), and reads and prunes build cache. `ContainerSummary` gains `imageId`, and usage is a pure frontend function over the images and containers queries. The events supervisor adds an `imagesChanged` hint. The frontend adds `features/images` (list page, details page) and reuses the containers page patterns.

**Tech Stack:** Rust (Bollard 0.21.1, serde, ts-rs), Tauri 2, React 19, TanStack Router/Query, Zustand, base-ui, Vitest via `vp test`. No new dependencies.

**Spec:** `docs/specifications/m4-images.md`. Read it first. FR, AC, and D numbers below refer to it.

## Global Constraints

- No new Rust or npm dependencies. The confirm dialog is the shadcn `alert-dialog` component generated onto the installed `@base-ui/react` (`pnpm dlx shadcn@latest add alert-dialog`); if the generator wants to add a package, stop and write the component by hand on `@base-ui/react/alert-dialog`.
- Work on branch `m4-images`, one commit per task, messages in the `git log` style (`Add … (M4 slice Sn)`).
- At the end of every task these pass: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` (pedantic is on), `cargo test --workspace`, `pnpm check`, `pnpm test`, `pnpm typecheck`.
- DTOs derive `ts_rs::TS` under `#[cfg_attr(test, derive(ts_rs::TS))]`, use `#[serde(rename_all = "camelCase")]`, and are added to the `bindings` test in `crates/docktide-core/src/lib.rs`. Regenerate with `DOCKTIDE_UPDATE_BINDINGS=1 cargo test -p docktide-core bindings`. `i64` byte counts get `#[cfg_attr(test, ts(type = "number"))]`, as `created_at` does today.
- Docker integration tests are `#[ignore = "requires Docker"]` in `crates/docktide-core/tests/docker.rs` and touch **only their own image ids** (see `TestImage` in Task 2). They never prune images or build cache, and never remove a tag on an image they did not commit.
- Commands are thin wrappers in `src-tauri/src/lib.rs`; `invoke` is called only from `src/lib/ipc.ts`.
- Server data stays in TanStack Query; sort, filters, and selection are UI state (Zustand for sort and filters, component state for selection).
- Sizes display with the existing `formatBytes` (binary units: MiB, GiB) from `src/features/container-details/format.ts`; the exact byte count goes in the cell's `title`. AC-1 compares bytes, not the CLI's decimal text.
- Usage "In use" states are `running`, `paused`, `restarting`: the `ACTIVE` set in `src/features/containers/list.ts` (export it; do not copy it).
- Copy, verbatim: `Images`, `N images · about Y unused`, `Build cache: X (Y reclaimable)`, `Build cache: empty`, `Build cache: size not reported by this Engine`, `Clear build cache`, `Remove all unused`, `Remove N selected`, `Remove`, `In use`, `Stopped (N)`, `Unused`, `Used by a, b and N more`, `Removed N images, about Y freed`, `Removed N of M. <name>: <message>`, `No images`, `No images match`, `Clear filters`, `This image no longer exists.`, `Back to images`.
- Verified on the dev host (2026-10-29, Engine 29.9.2, containerd store): `DELETE /images/<id>` on an image with two tags answers `409 … image is referenced in multiple repositories`. So multi-tag removal goes tag by tag (FR-3); there is no by-id shortcut.

## Review Focus

1. **A container is created from an image between the user's click and the removal.** Expected: no tag is touched, and the error toast shows the conflict. Test in Task 2: `remove_refuses_an_image_used_by_a_container_and_keeps_its_tags`.
2. **An image with two tags where only one tag was used to create a container** (`app:a` used, `app:b` not). Expected: the row is In use, and Remove all unused leaves both tags. Test in Task 5: `usage matches by image id, not by the tag the container names`.
3. **The same id is removed twice** (a second click, or an image removed in a terminal while the bulk run is going). Expected: the second removal succeeds silently (FR-3: 404 counts as removed). Test in Task 2: `removing_a_missing_image_is_ok`.
4. **An Engine that sends only the legacy `BuildCache` array.** Expected: size `null` and the Clear button still shown, never `Build cache: empty`. Tests in Task 3 (`legacy_only_response_is_not_reported`) and Task 5 (`build cache strip state`).
5. **Image and container events in the same 250 ms window.** Expected: one `containersChanged` and one `imagesChanged`, and image events are never published to the in-process container fan-out (the stats supervisor would treat image ids as containers). Test in Task 4: `image_events_coalesce_into_one_hint_and_are_not_published`.

- [ ] **Step 4: Implement `remove_image`**

Steps, in order:

1. `inspect_image(id)`; `NotFound` → `Ok(())`.
2. List all containers; if any has `image_id == id`, return `DockerError::Conflict { message: "image is used by <names>" }` (first three names, `and N more`) without removing anything.
3. No tags → `remove_image(id)` with `force: false`. Otherwise remove each tag with `force: false`, in `repo_tags` order. A `NotFound` on any call counts as removed.
4. If a tag fails after at least one succeeded, return `DockerError::Conflict { message: "Removed tags a, b; c: <message>" }`; if the first fails, return its error unchanged.
